analysis-video

Turn video into AI-readable context.

Convert lecture, screencast, and slide-based video into a single Markdown file an LLM can actually read: keyframes, timestamps, and transcript, aligned screen by screen. A command-line tool that runs entirely on your machine.

uvx analysis-video@latest analyze lecture.mp4

The problem

Subtitles are half the video

Ask an AI to analyze a lecture video and all it gets is the subtitles — the speech, and nothing that was written, drawn, coded, or shown on screen.

Slide-based teaching puts the claim on screen and the reasoning in speech. A subtitle track is an excellent record of that second half — a person wrote it, so the proper nouns and the numbers are right — which is exactly why this tool reads it when there is one. But nothing in it records which sentence belonged to which slide. Frames alone lose the explanation. You need both, aligned.

analysis-video samples frames by how much the screen changed rather than at a fixed interval, and writes an image of every distinct screen, the time range it was on screen, and the speech that happened during it — as one Markdown file you can grep, index, version, and hand to any model.

What you get

One Markdown file, one screen per entry

## 63.13-87.73s
![](read/scene_020_t0063.13.jpg)
![](read/scene_021_t0087.70.jpg)
N1 없이 커지면 BN이라는 값도 당연히 1 없이 커지게 됩니다. ...

One entry = one screen, or the screens a single sentence spanned. When a screen has two images they are its first and last appearance — for handwriting or progressive slides, the second one is the completed state. The transcript is distributed across screens exactly once, with nothing dropped.

The linked images are downscaled reading copies; originals stay at full resolution under frames/. That is a context-window decision, not a disk one: measured, a reading copy costs 4.17× fewer tokens than the full-resolution frame — the difference between a one-hour lecture that fits in a 1M-token window and one that does not. The opening paragraph of context.md states the image count and roughly what opening all of them costs, so a model can decide how many to open before opening any.

In your AI workflow

Your AI agent runs it — you just ask

You never type these commands. You ask your agent a question about a video; it reaches for analysis-video, gets back something it can actually read, and answers from what was on the screen — not just what was said over it.

The loop, end to end

The agent never has to work out what comes next: every command ends with the same next object telling it whether to run something, read something, or answer you. And next carries the price tag before the images — {"images": 6, "image_tokens": 2652} — so a model with a full context window can open the screens that were up longest and skip the rest, instead of finding out too late.

What you keep

The answer is not the only thing left over. Your agent's write-up is stored beside the video at reviews/<run>.md, stamped with the sha256 of the exact context.md it read. Ask again next week and the agent re-uses it instead of re-opening every image. Re-detect at a different threshold and it marks itself stale — the loop asks for a fresh reading rather than letting an old analysis quietly pass as current.

An analysis is not finished when context.md exists. It is finished when every unit has a review that still matches what it read — that is the moment next.do becomes "done".

What one actually looks like

A real review is committed in the repository: the agent's write-up of the 41-second demo clip → The header is generated by the tool; the body is the agent's. Read it for one line in particular — the clip's narration names two detection signals, the slide on screen names three, and the review catches that an agent working from the transcript alone would have gotten the answer wrong. That is the case for frames, made on the tool's own output instead of asserted. It reproduces with analysis-video analyze docs/media/demo-pipeline.mp4.

Install

Three ways, no ffmpeg

Decoding uses PyAV, which ships its own binaries. There is nothing to install at the system level.

uvx analysis-video@latest analyze lecture.mp4
uv tool install analysis-video
pip install analysis-video

@latest matters: uvx caches the version it resolved the first time and keeps running that one until told otherwise.

Do you need speech recognition?

The base install has no whisper backend, and most videos never need one. When the video has a subtitle beside it or a text track inside the container, that is where the dialogue comes from — no model is loaded, no weights are downloaded, and nothing touches the network.

Your videoWhat to install
has a subtitle beside it (lecture.ko.srt) or a text track inside the containerbase install — analysed end to end, offline
you name a subtitle yourself with --transcript FILEbase install
has no usable subtitle anywhereanalysis-video[stt]

Guessing wrong is cheap. analysis-video doctor reports the missing capability and still exits 0, and the only run that fails is a transcription that actually reached whisper — exit 4, with the install command in error.hint.

Setup, part two

One line teaches your agent the loop

Installing the package puts a command on your PATH. This puts the loop above into your agent's head — once, for every project folder you will ever open.

uvx analysis-video@latest install-skill

That writes a short Claude Code skill to ~/.claude/skills/analysis-video/. It is not a description of the tool — it is the instruction to run the loop: call agent-guide first, follow next until it says done, and do not stop at context.md. No plugin, no marketplace, no MCP server to keep running. For harnesses without a skill mechanism — Codex, Cline, Cursor, anything that reads AGENTS.md:

analysis-video install-skill --agents-file AGENTS.md

That inserts the guide between markers and replaces that block on re-run, so upgrading never leaves two conflicting copies in your rules file. The agent's authoritative reference is analysis-video agent-guide — a document generated from the actual code constants, so changing a threshold changes the documentation with it. Your agent reads the real values, never a stale copy of them.

Usage

Analyze, read, keep

# 1 — analyze (stages run in order, each one resumable)
analysis-video analyze lecture.mp4
# → lecture.mp4.analysis/runs/full/context.md

# 2 — your agent reads context.md and writes its analysis back
analysis-video review lecture.mp4 --write -

# 3 — reclaim what can be rebuilt
analysis-video clean lecture.mp4 --level images

# only part of a video? each range is an independent unit, never merged
analysis-video analyze lecture.mp4 --range 120-300 --range 900-1200

# a frame the detector had no reason to pick
analysis-video frame lecture.mp4 --at 421.8 --reason "why this moment matters"

Built for AI agents as the primary consumer, not humans: exactly one JSON object on stdout per call, decisions expressible through exit codes alone (0 ok · 2 bad input · 3 stage order · 4 something missing), absolute paths everywhere, and resumable stages. Every command ends with the same next object saying which step is due, so the caller never has to work it out.

How it works

Five stages, no model in the loop

This tool does not interpret anything. There is no LLM call anywhere in the pipeline — a subtitle file is read as written, Whisper is a speech-recognition model, and frame detection is pixel math. What the tool produces is readable material; deciding what it means is done by the AI agent that reads context.md. That is why the chain ends at review: the interpretation happens outside the tool, and review is where it is kept instead of evaporating with the chat session.

Where the transcript comes from

A subtitle written by a person beats any recognizer, so dialogue is taken from the first source that works: --transcript FILE you name, then every sidecar (.srt / .vtt / .smi) and container text track ranked as one list by language first, then Whisper. Candidates that cover under 30% of the video, hold fewer than 5 cues, run past the end, or are more than 30% roll-up (the signature of auto-generated captions) are rejected and the next one is opened. transcript.json records why each source was passed over, so you can always tell why Whisper ran. Nothing is translated — a language mismatch is reported, not silently rewritten.

Trusting the detector

How do you know it kept the right screens?

Frame selection is pixel math, not a model — but that only moves the question. A detector cannot judge its own output. So the optional GUI exists to let you judge it, and to turn that judgement into a number.

Mark what had to be extracted, then score the detector against it

Watch the video and press F at any moment that should have produced a frame. That writes a ground-truth flag to user_flags.json. The Compare report then matches your flags against what the detector actually kept, within a tolerance you set, and reports two numbers:

What it counts
recallthe share of your flags that the detector found — what it missed
precisionthe share of its detections that landed near one of your flags — what it kept for no reason

Both stay blank until you have flagged something — a detector scored against no ground truth is a number with nothing behind it. The tolerance defaults to 2 seconds, and clicking a row jumps playback to that row's ground-truth flag, so a number always leads back to the frame it is about. Export compare.json writes the comparison out, so a threshold change can be argued with a diff rather than an impression. That is what turns “raise the cut-area threshold” from a guess into a measurement.

It follows the CLI

The windows watch the analysis directory — metadata.json, transcript.json, and the output folder itself — and redraw when they change. Re-run analysis-video analyze with a different threshold in your terminal and the timeline, the gallery and the report update on their own; there is nothing to reopen, and there is no polling loop. Because frames empties and rebuilds the unit's folder, those windows go blank while the re-run is in flight and fill back in when it lands. One case still needs a restart: if you opened the GUI on a directory that had no analysis unit yet, the first frames run is not picked up.

The outputs that carry the analysis — state.json, transcript.json, metadata.json, frames.json — are written to a temporary path and swapped in with a single rename, so a run killed by a timeout leaves the previous versions whole rather than truncated. That is a property of the core, not a GUI feature: it holds whether or not you ever open a window. It does not cover everything — the detector caches, the run index and the context.md an agent reads are still written in place, since a re-run rebuilds them. So the GUI does not lean on it: a read that lands mid-write leaves that panel empty and retries on the next watch event.

You do not need any of this to use the tool. The GUI ships as a separate package with its own version (analysis-video-gui), so CLI-only users never download Qt. It exists for the moments when the honest answer to “did it pick the right screens?” has to be a number rather than a feeling.

Strengths and limits

What it is good at, and what it is not

Strengths

  • Runs entirely locally. No upload, no API key. The only network access is a one-time Whisper weight download — and a subtitled video never triggers even that.
  • No system dependencies. PyAV bundles its own decoders; no ffmpeg to install.
  • Adaptive sampling. Frames are chosen by screen change, not a fixed interval and not timestamps you supply.
  • Token-aware output. Reading copies cost 4.17× fewer tokens, and context.md states the cost before you open anything.
  • Resumable. A run cut off by a timeout picks up where it stopped.
  • Agent-native contract. One JSON object per call, meaningful exit codes, absolute paths, and a next object on every command.

Limits

  • Screen-stable content only. Lectures, screencasts, slide decks, coding tutorials, whiteboards. Continuously moving footage produces too many screen changes and is not the target.
  • Disk cost. The analysis directory is 1.9–2.8× the source, about 4.48 MB per minute. clean reports what is reclaimable before deleting anything.
  • Install size. 108 MB downloaded / 308 MB on disk; [stt] takes it to 326 MB / 1,180 MB — 476 MB of that a torch this tool never imports, pulled in unconditionally by an upstream dependency.
  • No Windows ARM64. opencv-python-headless publishes no wheel for it.
  • CUDA path unverified. The [cuda] extra resolves, but has not been run on real NVIDIA hardware.
  • No translation, and no interpretation. Dialogue is left in whatever language it is in, and the tool never summarizes — that is the reading agent's job.
  • No format migration. Analysis directories from an older version are refused with a clear error rather than half-read.

FAQ

Questions

Does it upload my video anywhere?

No. Video decoding, scene detection, and transcription all run locally. The only network access is the one-time download of Whisper model weights — and when the transcript comes from a subtitle file or subtitle track, even that never happens, so such a video can be analyzed on a fully offline machine.

Claude already summarizes YouTube videos. What is missing?

The screen. That summary comes from the subtitles — fine for a talking-head interview, lossy for anything taught on screen: the slide, the code, the diagram, the equation being worked out. This tool reads the same subtitles, but does not stop there: it restores the visual half and pins each line of speech to the screen it belongs to.

Gemini accepts video directly. Why would I use this?

Three reasons. Fixed-rate sampling is the wrong shape for screen-stable content: at the default 1 fps an hour of lecture is about 3,600 frames, nearly all duplicates, and Google's own docs tell you to hand-tune the rate down for lectures — this tool does that adaptively by detecting screen changes. Second, you get a file, not a one-shot API call: context.md can be grepped, indexed for RAG, committed, and re-read for free. Third, it works with models that take no video at all, and it never uploads yours.

My video already has subtitles. Will it use them, or run Whisper anyway?

It uses them, as long as they hold up: a sidecar file next to the video or a text track inside the container is preferred over Whisper, and --transcript FILE names one directly. Whisper is then never loaded, which is why that path also needs no [stt] extra and no network. Auto-generated captions and forced foreign-lines-only tracks are rejected, and that is the case where Whisper runs instead.

Do I need to install ffmpeg?

No. PyAV bundles its own decoders.

How big is the install?

Measured on macOS Apple Silicon: 108 MB downloaded, 308 MB on disk — no whisper backend, no torch. Adding [stt] takes it to 326 MB / 1,180 MB, and 476 MB of that is a torch this tool never imports, pulled in unconditionally by an upstream dependency. On Linux the extra costs about 70 MB rather than 218 MB. Whisper model weights are a separate download on first use.

How much disk does the analysis directory take?

More than the video: measured at 1.9 to 2.8 times the source, or about 4.48 MB per minute — roughly 0.27 GB for a one-hour lecture. analysis-video clean reports what is reclaimable before deleting anything; on a measured sample --level images took a directory from 9.8 MB to 1.4 MB. It never touches reviews, transcript.json, the reading copies context.md links to, or frames you ordered with frame --at.

Is there an MCP server?

No, deliberately. The CLI already returns structured JSON with an exit-code contract; an MCP wrapper around it would be a one-to-one restatement with an extra process to keep running. install-skill gives agents the same discoverability with none of that.

Which video formats work?

Whatever PyAV and FFmpeg decode — MP4, MOV, MKV, WebM, and so on.

Does it work on non-slide video?

It is designed for screen-stable content: lectures, screencasts, slide decks, coding tutorials, whiteboard recordings. Continuously moving footage produces many screen changes and is not the target.
